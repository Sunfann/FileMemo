# 修复记录：文件/文件夹移动后备注路径未更新、无法打开

> 目标项目：**FileMemo（文笺）**（WPF，`net8.0-windows10.0.19041.0`）
> 报告日期：2026-09-29
> 现象来源：用户截图 `PixPin_2026-09-29_14-14-17.png`

---

## 1. 现象

1. 文件在资源管理器中已被移动到其它位置（如子目录 `s\`），但「文件/文件夹备注」里显示的**文件路径仍是旧路径**。
2. 此时点击「**打开文件**」「**定位**」**无法正常打开**（指向已不存在的旧路径）。
3. 右侧「时间线」中只有 `annotated`（新增备注）与 `edited`（编辑），**没有 `moved` 记录** —— 说明这次移动从未被应用感知。

## 2. 根因

移动/重命名的路径同步**完全依赖运行时监听事件**驱动：

| 通道 | 文件 | 触发条件 |
|---|---|---|
| USN Journal | `Services/UsnJournalService.cs` → `ApplyToRepository` | 应用运行中且卷为 NTFS |
| FileSystemWatcher | `Services/FileWatcherService.cs` → `OnRenamed` | 应用运行中且目录在监听范围 |

因此当文件是在**应用未运行期间**（或监听漏事件、非 NTFS 无权限等）被移动时：

- 监听器收不到任何事件 → 库中 `file_ref.path` 保持旧值；
- 「打开文件 / 定位」直接使用 `row.FileRef.Path`（`MainWindow.xaml.cs`、`FloatingNoteWindow.xaml.cs`）→ 指向不存在的旧路径而失败。

即：**缺少「被动校正」机制**——只在能收到事件时同步，一旦漏事件就永久失配。

## 3. 修复方案

新增按需 + 启动两条校正路径，全部基于既有指纹能力（同卷 NTFS File ID / 内容哈希），不改变数据模型。

### 3.1 `Services/FingerprintService.cs`
新增 `string? TryLocate(FileRef fr)`：为路径已失效的记录找回当前真实路径。
- 原路径仍有效 → 直接返回；
- 同卷主指纹：`OpenByFileId` 打开旧路径所在卷 + File ID 的句柄，用 `GetFinalPathNameByHandle` 反查真实路径，并校验 File ID 与卷 GUID 一致后再采信；
- 跨卷兜底：完整哈希在库内**唯一**命中且目标确实存在时采信；
- 找不到返回 `null`（调用方据此提示）。

### 3.2 `Services/FileWatcherService.cs`
- 新增 `string? Reconcile(FileRef fr)`：路径失效时调用 `TryLocate` 找回并回写 `file_ref.path`、清除 `offline`、写 `moved` 时间线；若目标为文件夹，同时用 `RebindPathPrefix` 迁移其下子项备注路径，并把新目录纳入监听。
- 新增 `int ReconcileAll()`：遍历所有备注做一次全量校正。
- `Start()` 开头调用 `ReconcileAll()`：**启动即校正**，弥补应用未运行期间发生的移动/重命名。

### 3.3 `Views/MainWindow.xaml.cs`
- `OpenFile_Click` / `RevealFile_Click` 先经 `EnsureFileRefCurrent(fr)` 取「当前有效路径」：路径失效时调用 `Reconcile` 找回并刷新列表/详情，再打开；确实找不到时弹提示「文件已被移动或删除」。

### 3.4 `Views/FloatingNoteWindow.xaml.cs`
- `Open_Click` / `Reveal_Click` 采用同样的 `ResolveCurrentPath(fr)` 校正后再打开。

## 4. 修改文件清单

| 文件 | 变更 |
|---|---|
| `Services/FingerprintService.cs` | 新增 `TryLocate` |
| `Services/FileWatcherService.cs` | 新增 `Reconcile` / `ReconcileAll`；`Start()` 启动校正 |
| `Views/MainWindow.xaml.cs` | 「打开/定位」前校正路径 + 失效提示 |
| `Views/FloatingNoteWindow.xaml.cs` | 「打开/定位」前校正路径 + 失效提示 |

## 5. 预期效果

- 文件在**应用关闭期间**被移动 → 重新打开应用（或点击打开/定位）后，备注路径自动跟随到新位置，时间线记录 `moved`，并且可以正常打开。
- 文件被彻底删除 → 打开/定位时明确提示「文件已被移动或删除」，而不是静默失败。

## 6. 验证建议

1. VS 2022 打开 `FileMemo.sln`，`dotnet build src\FileMemo.App\FileMemo.App.csproj`。
2. 为某文件添加备注 → 关闭应用 → 在资源管理器把该文件移动到别的目录 → 重新打开应用：
   - 备注路径应自动更新为新位置；
   - 点「打开文件」应能正常打开。
3. 运行时移动（USN/FSW 生效路径）行为不变，仍由原监听逻辑实时同步。

# 追加功能：文件备注删除

> 需求：为文件 / 文件夹备注提供删除能力。

## 1. 交互入口

- **主窗口**右侧「文件 / 文件夹备注」编辑器：在「保存备注」右侧新增「**删除备注**」按钮。
- **快捷键备注弹窗**（`FloatingNoteWindow`）：在「保存」右侧新增「**删除备注**」按钮。

两者点击后均弹出二次确认（`MessageBox` Yes/No），确认后删除备注：
- 主窗口：清空选中、刷新列表与详情；
- 弹窗：删除后自动关闭。

**不会删除磁盘上的文件本身。**

## 2. 数据层实现

`Data/Repository.cs` 新增 `bool DeleteAnnotation(string fileRefId)`（事务内）：
- 删除 `annotation` 本体；
- 清理伴随数据：`timeline`（object_id）、`sidecar`（file_ref_id）、`record_link`（from/to）；
- 各伴随表容错（表不存在时忽略）；
- 返回是否确实删除（未命中返回 `false`）。

**保留 `file_ref` 与 `fingerprint`**：它们描述文件本身，列表与文件树均由 `annotation` 驱动，
故删除备注不影响文件树展示；保留指纹还便于用户之后重新添加备注时复用（无需重新计算）。

## 3. 修改文件清单

| 文件 | 变更 |
|---|---|
| `Data/Repository.cs` | 新增 `DeleteAnnotation` |
| `Views/MainWindow.xaml` | 备注详情底部新增「删除备注」按钮 |
| `Views/MainWindow.xaml.cs` | 新增 `DeleteAnnotation_Click`（确认 + 删除 + 刷新） |
| `Views/FloatingNoteWindow.xaml` | 底部新增「删除备注」按钮 |
| `Views/FloatingNoteWindow.xaml.cs` | 新增 `Delete_Click`（确认 + 删除 + 关闭） |

## 4. 验证建议

1. 为某文件添加备注 → 主窗口点「删除备注」→ 确认 → 列表/详情应清空，文件树仍显示该文件。
2. 快捷键弹窗编辑备注 → 点「删除备注」→ 确认 → 弹窗关闭，重新呼出时备注为空（未备注状态）。
3. 删除后重新「添加文件备注」指向同一文件 → 应能正常创建新备注。
